## 1. 范围（一句话）

为「零零守护者」双人闯关游戏产出一份**可施工的完整重写设计方案**：保留"双人协作收集宝石→同门通关"的核心幻想，重构为支持 **1/2/3/4 人**、**键位可配置**、**支持手柄**的 15 关作品，并给出性能、素材、特效、动画的细化规格。

**主目标**：让工程拿着本文档可以直接开工，且每个数字都能从配置复算出来。
**次要目标（按权重排序）**：① 手感确定性（可回放）② 1–4 人同屏不降帧 ③ 素材可替换不改名 ④ 便于后续加关。

**跳跃高度推导**（由上面常量推出）：起跳帧 `G_speed=-4`；此后每帧 `G_speed += 0.5`、`y += G_speed`、`y -= 4`（按住）。
第 n 帧净位移 `= -8 + 0.5n`，上升持续到 n=15（`n<16`），总升高
`Σ(8-0.5n), n=1..15 = 120 - 60 = **60 px = 1.2 格**`。
松手后 `direction_W=False`，不再 -4，直接自由落体。
→ **这是"火箭跳/悬停跳"，不是定高跳**，是旧版手感的核心特征，重写时保留为可切换开关。

## 3. 幻想与支柱

**幻想**：两个（或更多）能力互补的守护者，在方块世界里靠"分工"而非"各自变强"去解开地形——一个人清路，一个人搭路。

**三根支柱**（冲突时按顺序让位）：

1. **分工优于操作**——胜利来自"谁去做什么"的决策，而不是手速。
2. **同屏可读**——任何时刻一眼看清：宝石剩几颗、队友在哪、危险在哪。
3. **失败便宜**——死亡 1 秒内回到可玩状态，不打断节奏。

**核心循环（一句话）**：玩家用各自专属动词改变地形与清点敌人 → 地形/宝石状态变化 → 双人同时站上传送门 → 解锁下一关。

**三层循环**

| 层 | 周期 | 内容 | 奖励节奏 |
|---|---|---|---|
| 瞬时 | 秒 | 移动/跳/射/造箱 → 地形改变 → 能去新地方 | 每次"够到了"的即时反馈 |
| 单局 | 1–3 分钟 | 清完宝石 → 双人同门 → 通关 | 通关结算 + 星级 |
| 元 | 天 | 15 关推进 + 解锁新角色/皮肤 | 关卡解锁、星级收集 |

**张力来源**：**协作稀缺**（有些机关必须两个人同时/分别在两处）。这是要重点保护的——1 人模式必须靠"切换角色"来模拟，不能退化成单人爽游。

## 4.1 显示与窗口模式

### 4.1.1 三种模式

| 模式 | 说明 | 触发 |
|---|---|---|
| `WINDOWED` | 带边框窗口，可拖拽调整 | 默认 |
| `FULLSCREEN` | `pygame.FULLSCREEN`，独占 | F11 / 设置项 |
| `BORDERLESS` | 无边框全屏（Alt+Tab 更快） | 设置项 |

### 4.1.2 分辨率策略（关键：逻辑分辨率固定）

**逻辑分辨率恒为 1600×900**，所有关卡坐标、物理、碰撞都在这个坐标系里算，与窗口实际大小**完全无关**。渲染时：

```
1. 全部内容画到离屏 Surface(1600, 900)
2. 按实际窗口尺寸等比缩放，宽高比不一致时 letterbox 补黑边
3. scale = min(win_w / 1600, win_h / 900)
4. 鼠标坐标需反变换：logical = (screen - offset) / scale   ← 否则点击偏移
```

**规则闭口**：
- 切换模式时**只重建显示 Surface，不重建任何游戏状态** → 全屏切换不会丢进度、不会重置关卡。
- 缩放后鼠标点击必须做反变换（上面第 4 步），否则 UI 点不准。这是窗口缩放最常见的 bug。
- 全屏模式下 `scale` 可能为 1.0（1080p 屏 1600×900 → 实际是 1920×1080，scale=1.2）。

### 4.1.3 校验

| 用例 | 通过标准 |
|---|---|
| 游戏中 F11 切换 10 次 | 关卡进度、宝石数、角色位置全部不变，无异常 |
| 1600×900 / 1920×1080 / 1280×720 三种窗口 | 画面无拉伸变形（宽高比保持 16:9），黑边对称 |
| 窗口化下点击 UI 按钮 | 命中准确（坐标反变换生效） |
| 全屏下 Alt+Tab 再切回 | 不黑屏、不崩溃 |

## 5. 系统地图

```
输入层(键盘/手柄 → Action)  →  玩家控制层(动词→意图)
                                     ↓
                         物理层(移动/重力/碰撞)  ←→ 地形(TileMap)
                                     ↓
              交互层(宝石/刺/门/传送门/箱子/子弹)
                                     ↓
                         敌人层(巡逻怪/Boss)
                                     ↓
                         规则层(宝石计数/通关判定/死亡)
                                     ↓
                     表现层(渲染/动画/粒子/音效/HUD)
```

**依赖方向单向**：表现层只读，不写状态。规则层不直接改物理，只发事件。

## 6. 每帧结算顺序（工程与策划必须读到同一个结果）

固定步长 `FIXED_DT = 1/60 s`，累加器最多追帧 5 次（防死亡螺旋）。每个逻辑帧按**严格顺序**执行：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 采样输入 | 键盘 + 手柄 → 每个玩家的 Action 集合（含 pressed / held / released） |
| 2 | 计时器递减 | 土狼时间、跳跃缓冲、无敌帧、射击冷却 |
| 3 | 玩家水平移动 + X 轴碰撞解算 | 先 X 后 Y，与旧版一致 |
| 4 | 玩家垂直移动 + Y 轴碰撞解算 | 落地则 `vy=0`、`grounded=True`、重置跳跃状态 |
| 5 | 触发物判定 | 宝石收集 / 刺致死 / 传送门 / 小传送门 / 压力板 |
| 6 | 子弹更新与命中 | 命中怪物、命中可破坏箱、出界回收 |
| 7 | 敌人更新 | 巡逻位移、边界转向 |
| 8 | 通关判定 | 全玩家在门内 **且** 宝石数 ≤ 0 |
| 9 | 死亡判定与重生 | 见 §10.7 |
| 10 | 渲染 + HUD | 只读上一步状态 |

**结算顺序冲突规则**：若同一帧既"吃到宝石使宝石清零"又"站在门内"，**步骤 5 先于步骤 8**，因此本帧即可通关（设计为奖励精准操作）。
若同一帧既"踩到刺"又"站在门内"，**步骤 5 内部刺判定优先于门判定** → 死亡优先，不通关。

## 7. 输入系统（本轮新增需求的重点）

### 7.1 设计原则

输入层只产出**语义动作（Action）**，游戏逻辑永不直接读键码。这样键位可配置、手柄支持、回放系统三者共用同一条链路。

### 7.2 Action 定义

| Action | 类型 | 说明 |
|---|---|---|
| `MOVE_LEFT` / `MOVE_RIGHT` | held | 水平移动 |
| `JUMP` | pressed+held | 跳（held 期间按 §9 规则持续上冲或可变跳高） |
| `CROUCH` | held | 下蹲（进传送门 / 部分技能的触发条件） |
| `SKILL_A` | pressed 或 held | 英雄**技能 A**（由所选英雄决定，见 §8） |
| `SKILL_B` | pressed 或 held | 英雄**技能 B**（由所选英雄决定，见 §8） |
| `SWAP` | pressed | 单人模式下切换所控角色 |
| `PAUSE` | pressed | 暂停 |

> `SKILL_A/B` 是**语义动作**，不含具体含义。同一按键在不同英雄身上意义不同，逻辑层只读 Action、不读键码。这是"英雄可选"能成立的前提。

### 7.3 玩家Slot与分配

| 模式 | Slot 数 | 分配规则 |
|---|---|---|
| 单人 | 2 个角色 1 个 Slot | 玩家控制 Slot0，`SWAP` 在角色间切换；未被控角色进入 **跟随态**（见 §8.3） |
| 双人 | 2 | Slot0=P1（弓箭），Slot1=P2（搬砖） |
| 三人 | 3 | + Slot2=P3（新角色，见 §8.2） |
| 四人 | 4 | + Slot3=P4 |

**Slot 绑定优先级**：手柄 > 键盘。同一 Slot 若已绑手柄，键盘输入仍可并行（不互斥），避免"朋友抢键盘"卡死。

### 7.4 默认键位（三人/四人沿用既有四人版，来源【给定】§2.5）

| Slot | 左 | 右 | 跳 | 蹲 | 技能A | 技能B | 切换 |
|---|---|---|---|---|---|---|---|
| P1 | A | D | W | S | J | K | Tab |
| P2 | ← | → | ↑ | ↓ | 1 | 2 | — |
| P3 | J | L | I | K | U | O | — |
| P4 | 小键盘4 | 小键盘6 | 小键盘8 | 小键盘5 | 小键盘7 | 小键盘9 | — |

**变更说明**：旧版 P1 的 `S` 同时是"下蹲"和"射击"，存在语义歧义。新方案把射击移入 `SKILL_A`，`S`/`↓` 回归纯下蹲 —— 这一改动同时解决了【原 Q3】。四人分区：P1 左手区、P2 方向键区、P3 右边字母区、P4 小键盘区，四只手互不重叠。

### 7.5 手柄支持规格

| 项 | 规格 |
|---|---|
| API | `pygame.joystick`，启动时 `pygame.joystick.init()` |
| 摇杆 | 左摇杆 X 轴 / 十字键 → `MOVE_LEFT/RIGHT`；Y 轴向下 → `CROUCH` |
| 按键映射 | A(0)=JUMP，X(2)=SKILL_A，B(1)=SKILL_B，Y(3)=SWAP，Start(9)=PAUSE |
| 扳机 | LT/RRT 轴 > 0.5 → CROUCH |
| 死区 | `DEADZONE = 0.25`（轴绝对值 < 0.25 视为 0） |
| 多手柄 | `joy.get_instance_id()` 绑定 Slot；`JOYDEVICEADDED` 时自动分配给空 Slot |
| 热插拔 | `JOYDEVICEREMOVED` 时该 Slot 释放为键盘可用，游戏**不暂停、不崩溃** |
| 手柄缺失 | 无手柄时全部走键盘，不弹任何提示 |

### 7.6 键位配置持久化

存 `config/input.json`，结构：

```json
{
  "slots": [
    {"device": "keyboard", "bindings": {"MOVE_LEFT": ["K_a"], "JUMP": ["K_w"], "ATTACK": ["K_f"]}},
    {"device": "keyboard", "bindings": {"MOVE_LEFT": ["K_LEFT"], "JUMP": ["K_UP"]}},
    {"device": "joystick", "guid": "03000000...", "bindings": {"JUMP": ["btn:0"], "MOVE_LEFT": ["axis:0:neg"]}}
  ]
}
```

**校验规则**：① 同一 Slot 内同一 Action 不得重复绑定；② 不同 Slot 允许相同键（同屏共用）；③ 每个 Slot 的 `MOVE_LEFT/RIGHT/JUMP` 为必填，缺则用默认值补；④ 手柄按 `guid` 回退，未匹配 guid 时按 Slot 序号回退。

## 8. 英雄与双技能系统

### 8.1 设计原则

1. 每个英雄有 **2 个专属技能**；6 个英雄共 **12 个技能，互不重复**（选择才有意义）。
2. **基础移动（走/跳/蹲）对所有英雄完全一致** —— 技能只加"额外能力"，不改基础手感。这是关卡可控的前提。
3. 技能按用途分三类：**攻击**、**建造**、**机动**。
4. 每个英雄带一个 `gem_affinity`（宝石亲和），决定它能吃哪种宝石。
5. 技能不得制造"永久捷径"，约束见 §8.5。

### 8.2 英雄表

| 英雄 | 定位 | 技能 A | 技能 B | 宝石亲和 | 解锁 |
|---|---|---|---|---|---|
| **弓箭手·零零** | 远程输出 | 射击（子弹） | 长跳（滑翔远跳） | 绿 | 默认 |
| **搬运工·砖哥** | 建造 / 搭路 | 放箱子 | 回收箱子（踩箱消失并返还） | 黄 | 默认 |
| **忍者·影** | 高机动近战 | 连跳（二段跳） | 近战突刺 | 通用 | 通关 L4 |
| **门师·隙** | 传送 / 调度 | 放传送门（成对） | 换位门 | 通用 | 通关 L7 |

| 宝石 | id | 可收集的英雄 |
|---|---|---|
| 绿宝石 | 5 | `gem_affinity = green` 或 `any` |

**规则闭口**：
- P1/P2 不再固定对应颜色 —— 换英雄就换归属，这是"英雄可选"的必然结果。
- **关卡加载校验（新增第 6 条）**：若当前队伍**没有任何英雄**能收集某种仍存在的宝石 → 校验器报错并在选人界面提示"本关需要 X 色英雄"。防止出现"宝石永远吃不完"的死局。

### 8.5 平衡约束（防止技能破坏关卡设计）

用户要求的技能池里有「放传送门 / 连跳 / 长跳」，这些**天然会破坏关卡难度**。必须先用规则锁住：

**约束 1 — 垂直缺口 ≥ 5 格**（v0.2 修订）
由 §8.3 推导：任何单一机动技能的最大垂直增益是 `130（一段跳）+ 75（二段跳）= 205 px`。
> **规则**：关卡中"必须靠建造才能通过"的缺口，高度必须 **≥ 5 格 = 250 px**。因为 `250 > 205`（余量 45 px），所以二段跳/长跳/悬浮**都不可能替代建造**。这条是数值闭口的，不是靠自觉。
>
> ⚠️ **为什么要改**：跳跃高度由 110 → 130 px 后，原"4 格 = 200 px"被 205 px **突破**（约束失效）。
> 不改的话，忍者二段跳就能跳过所有建造关，L3/L6/L10 的教学与解谜会全部失效。
>
> **可行性校验**：250 px 缺口，玩家每级跳跃力 130 px → 放 **2 级箱子台阶**（每级 125 px）即可通过；
> 团队共享箱子 12 个，足够。可行。

**约束 2 — 传送门不能悬空搭桥**
传送门只能贴在实体墙面上（id 1/2），不能凭空放置 → 无法在深渊上"造桥"。

**约束 3 — 建造资源是团队共享的**
箱子库存为**团队共享**，上限 `TEAM_CRATES = 12`（不是每人 12）。四人全选搬运工也不会出现"48 个箱子堆满地图"。

**约束 4 — 能力等价类（用于关卡标注，不强制）**
关卡可标 `required_abilities`，选人界面给"推荐"，但不强制锁定 —— 玩家可用等价技能绕过。

| 能力类 | 提供该能力的技能 |
|---|---|
| `ranged_attack` | 射击、冲击波 |
| `melee_attack` | 近战突刺、重踏 |
| `build` | 放箱子、举箱投掷 |
| `mobility` | 长跳、连跳、悬浮、放传送门 |
| `utility` | 回收箱子、换位门 |

### 8.6 英雄选择流程

```
主菜单 → 人数选择（1/2/3/4）→ 英雄选择 → 关卡选择 → 开始
                                    ↑
              每个 Slot 一张卡片：←/→ 切换英雄，确认键锁定
```

| 规则 | 说明 |
|---|---|
| 可否重复 | **允许**重复英雄（4 人全选弓箭手合法） |
| 锁定 | 全部 Slot 确认后进入；10 s 无操作自动确认当前选择 |
| 未解锁 | 灰显 + 显示解锁条件（如"通关 L7 解锁"） |
| 单人模式 | 选 **2 个**英雄（主控 + 跟随），游戏中 `SWAP` 切换 |
| 中途更换 | 关卡内不可更换；回选关界面可重选 |

### 8.7 玩家状态机（闭合）

```
IDLE ──MOVE──> RUN ──JUMP──> AIR ──落地──> IDLE
  │              │             │
  └──CROUCH──> CROUCH          └──踩刺/被怪碰/掉出屏──> DEAD
  │
  ├──举箱──> CARRY ──SKILL_B──> IDLE（投出）
  │
  └──(单人模式被切走)──> FOLLOW ──SWAP──> IDLE
DEAD ──0.8s──> RESPAWN(出生点) ──> IDLE
```

| 状态 | 可进入 | 可退出 | 边界处理 |
|---|---|---|---|
| IDLE/RUN/AIR/CROUCH | 常规 | 常规 | — |
| **CARRY（持箱）** | 重锤面前有箱时按 `SKILL_B` | 再按 `SKILL_B` 投出；被怪碰到 → 掉落箱子（角色不死） | 移速 ×0.7；持箱时**不可再放箱** |
| FOLLOW（跟随态） | 仅单人模式切走时 | `SWAP` 切回，或被怪碰时自动切回 | 跟随态角色**不可被怪杀死**（否则单人模式会莫名团灭） |
| DEAD | 踩刺 / 碰怪 / 掉出屏幕下沿 | 计时到自动退出 | 死亡期间该 Slot 输入被忽略 |
| RESPAWN | DEAD 结束 | 立即 | 回到本关出生点，宝石进度**不回退** |

**单人模式的通关规则闭合**：单人模式下"全玩家站门"无法满足，改为 **所控角色站门 + 跟随态角色自动被吸附到门内** 即判定通关。规则与双人模式共用同一段代码（跟随态角色的位置在判定前被强制同步到门中心）。

## 9. 物理与移动规格

### 9.1 单位与换算

内部一律用 **px/s 与 px/s²**，固定步长 `FIXED_DT = 1/60 s`。与旧版帧单位的换算：

```
px/frame × 60        = px/s
px/frame² × 3600     = px/s²
```

### 9.2 推荐数值（【推导】）

设计目标：**能稳定跳上 2 格（100 px）高台**，且跳跃观感 = **约 1.7 倍角色身高**。

> ⚠️ **v0.2 修订（必须看）**：角色改用 Kenney 素材后，实际高度由 60 px 变为 **76 px**
> （素材有效内容 81×97，而地形块 64 → 角色高 = 1.52 格，见 `ASSETS_EXTERNAL.md §14`）。
> 若沿用 110 px 跳跃，"跳跃高度 ÷ 角色身高"会从 1.83 倍掉到 **1.45 倍**，手感明显变钝。
> 因此：跳跃高度上调至 **130 px**，贴图由 40×60 改为 **50×60**（宽高比 0.833 ≈ 素材 0.835，零变形）。

| 量 | 符号 | 值 | 推导 |
|---|---|---|---|
| 重力 | `GRAVITY` | **1800 px/s²**（= 0.5 px/帧²，与旧版一致） | 给定基线 |
| 起跳速度 | `JUMP_VELOCITY` | **-684 px/s**（= -11.4 px/帧） | `√(2·g·h) = √(2×1800×130) ≈ 684` |
| 最大下落 | `MAX_FALL` | **1200 px/s**（= 20 px/帧） | 需 < TILE(50)，防穿透 |
| 水平速度 | `MOVE_SPEED` | **260 px/s**（= 4.33 px/帧） | 见下 |
| 跳跃切断 | `JUMP_CUT` | **0.45** | 松键时 `vy *= 0.45`，实现可变跳高 |
| 土狼时间 | `COYOTE_TIME` | **0.10 s**（6 帧） | — |
| 跳跃缓冲 | `JUMP_BUFFER` | **0.12 s**（≈7 帧） | — |

**算例（可复算）**：

```
上升时间 t_up = |JUMP_VELOCITY| / GRAVITY = 684 / 1800 = 0.380 s
跳跃高度 h    = JUMP_VELOCITY² / (2·GRAVITY) = 684² / 3600 = 467856/3600 = 129.96 px
             = 129.96 / 50 = 2.60 格  ✓ 满足"稳定跨 2 格"
滞空总时长    = 2 × t_up = 0.760 s
水平跨距      = MOVE_SPEED × 滞空 = 260 × 0.760 = 198 px = 3.95 格  ✓ 满足"跨 3 格坑"
跳跃观感      = 130 / 76（角色实际高）= 1.71 倍身高  ✓ 与旧版 1.83 倍接近
穿透校验      = MAX_FALL × FIXED_DT = 1200/60 = 20 px < TILE(50) ✓
```

### 9.3 碰撞盒（明确定义，修正旧版）

| 实体 | 碰撞盒 | 来源 |
|---|---|---|
| 玩家 | 贴图 **50×60**、碰撞盒 **44×56**（左右各收 3，底部收 4） | 【推导】v0.2 修订：贴图宽高比 `50:60 = 0.833` ≈ 素材 `0.835`，零变形；碰撞盒略收窄避免贴墙卡死 |
| 地刺 | **50 × 20**，位于格子下部（偏移 y+30） | 【给定】旧版 `row*BLOCK+30, BLOCK-30` |
| 箱子/墙/砖 | 50 × 50 | 【给定】 |
| 宝石 | 50 × 50（触发区，非阻挡） | 【给定】 |
| 传送门 | 100 × 150 | 【给定】 |

### 9.4 X/Y 分轴解算

```
move_x(dx): 位置 += dx → 查询重叠的 SOLID 格 → 有则回退到贴合位置，vx = 0
move_y(dy): 位置 += dy → 查询重叠的 SOLID 格
            → dy>0（下落）: 吸附到格子顶面，vy = 0，grounded = True
            → dy<0（上升）: 吸附到格子底面，vy = 0（撞头）
```
**查询范围**：只查玩家 AABB 覆盖的格子（`floor(left/TILE) .. floor(right/TILE)`），**不做 576 格全扫**。

### 9.5 火箭跳开关（保留旧版手感）

配置项 `physics.rocket_jump: bool`。
- `true`（复刻旧版）：按住跳键期间每帧额外上冲 `ROCKET_THRUST = 240 px/s`（= 4 px/帧），配合 `GRAVITY` 得到 §2.2 的 60 px 悬跳曲线。
- `false`（推荐默认）：定高跳，用 §9.2 数值。
建议 **L1–L3 用 `true`** 以便和旧版手感对齐、**L4 起用 `false`**，或整体统一为 `false`——标记为【开放 Q5】。

```
参数: x, y(固定), start, end, speed=2 px/帧 = 120 px/s

```
**修正**：用 `>=`/`<=` 替代旧版 `==`，并加载时校验 `(end-start) % (speed_px_per_frame) == 0`，不满足则报关卡校验错误。

### 11.3 教学顺序（与第一个必需动词一致）

| 关 | 教的动词 | 教学手法 | 成功信号 | 失败信号 |
|---|---|---|---|---|
| 1 | 移动/跳/收集 | 宝石放在跳跃可达的 1–2 格处，无死亡可能 | 吃到 2 颗→门亮起 | 无（L1 不放任何致死物） |
| 2 | 分工/射击 | 绿宝石只在 P1 够得到的高台，黄宝石只在 P2 侧 | 两种宝石都吃到 | 提示"这颗宝石只有弓箭手能吃" |
| 3 | 放箱 | 一个 3 格高台，不放箱绝对上不去 | 站上高台 | 掉落不致死，只回退 |
| 4 | 躲避 | 刺阵只有一条安全路径 | 无伤通过 | 死亡 0.8 s 重生，宝石不回退 |

**失败恢复原则**：任何死亡都**不回退宝石进度**（只重置角色位置）；全体死亡才重置地形。这样"失败便宜"支柱成立。

### 11.4 关卡数据格式（内容与规则分离）

关卡为纯数据 JSON，调参不改代码：

```json
{
  "id": 4,
  "name": "刺阵",
  "theme": "grass",
  "tile_size": 50,
  "grid": { "cols": 32, "rows": 18 },
  "tiles": [[0,0,1,2,...], ...],
  "spawns": { "p1": [0,500], "p2": [50,500], "p3": null, "p4": null },
  "portal": [1500, 0],
  "mini_portals": [[-100,600], [-100,750]],
  "monsters": [{"x":700,"y":250,"start":400,"end":1100,"speed":2}],
  "required_abilities": ["build"],
  "build_gap_min_rows": 5,
  "physics_profile": "classic"
}
```

**加载时强制校验**：
1. `tiles` 尺寸必须等于 `grid`；
2. `(end - start) % speed == 0`（怪物边界对齐）；
3. 宝石数 > 0；
4. `portal` 必须在网格范围内；
5. 出生点不得落在 SOLID 格内（否则自动上移到最近空格）；
6. **所有"必须靠建造通过"的垂直缺口高度 ≥ `build_gap_min_rows`（默认 5 格 / 250 px）** —— 见 §8.5 约束 1，防止机动技能绕过建造；
7. **当前队伍中必须存在能收集每种宝石的英雄** —— 见 §8.4，防止死局。

### 13.2 补齐途径（按优先级）

1. **自制/改色**：P3/P4 直接由 P1/P2 换色生成（Pillow 批量 hue shift），零许可风险。
2. **开源素材站**（需逐项确认许可证后再入库）：OpenGameArt、Kenney 平台者素材包、itch.io 的 CC0 资源。
3. **程序化生成**：粒子、闪光、涡流用 Pillow/numpy 运行时生成，不占仓库体积。

**素材入库规范**：
- 统一目录 `assets/img/`、`assets/wav/`、`assets/font/`，**路径全小写**，代码里只出现小写（消除 `Img/` vs `img/` 混用）。
- 每个素材配 `assets/manifest.json`，记录 `path / size / md5 / license / source_url`。缺 `license` 的素材**不得入库**。
- 运行时统一 `.convert_alpha()` 一次并缓存，不在循环里重复加载。

## 15. 性能预算与优化

### 15.1 预算（1600×900 @60 FPS，每帧 16.67 ms）

| 模块 | 预算 | 说明 |
|---|---|---|
| 逻辑 + 物理 | 3.0 ms | 4 玩家 × 分轴解算 |
| 碰撞查询 | 2.0 ms | 只查 AABB 覆盖格（≤ 12 格/玩家） |
| 渲染 | 8.0 ms | 背景 1 次 blit + 可见格 + 实体 |
| 音频 | 0.5 ms | 事件驱动 |
| 余量 | 3.17 ms | — |

### 15.2 必须修的性能问题（实测）

| 问题 | 现状 | 修法 |
|---|---|---|
| **每帧重建字体** | `level.py:126-127` 每帧调用 `pygame.font.Font()` 2 次 + `render()` | 字体与已渲染文本**启动时预建并缓存**；数字变化时只重渲染数字 |
| **每帧 print** | `level.py:138` 每个 event 都 `print(mouse_x, mouse_y)` | 删除；改用 `logging.debug` |
| **全图扫描碰撞** | 每帧 576 格 × 2 玩家 | 改为 AABB 覆盖格查询 |
| **递归重开** | 死亡递归调用主循环 | 状态重置（§10.7） |
| 贴图未 convert | 每次 `image.load` 后直接 blit | 加载时 `convert_alpha()` 并缓存 |

### 15.3 帧率稳定性

- 固定步长 + 累加器，最多追 5 帧。
- 掉帧时**不做**物理补偿跳过（保证确定性/可回放）。
- 提供 `--bench` 模式输出 p50/p99 帧时间。

### 19.4 三种视角的结论

- **工程视角**：第一条无法照实现落地的规则是 B2（递归重开），它决定了主循环架构，必须先定。
- **玩家视角**：第一处目标不清的地方是**英雄选择**——6 个英雄 × 2 技能，新玩家不知道该选谁。已在 §8.6 用"推荐提示"缓解，但仍需在选人界面加一句话定位说明（如"砖哥：负责搭路"）。
- **分析师视角**：第一个无法复现的数字是跳跃高度——旧版 60 px、v0.1 的 110 px、v0.2 的 130 px，三者都有完整推导链（§2.2、§9.2）。**130 px 不是随意上调**，而是为抵消 Kenney 角色变高 27%（60→76 px）做的补偿，目标是保住"1.7 倍身高"的跳跃观感。
- **平衡视角（本次新增）**：最大风险是**技能让关卡失效**。已用三条硬约束闭口（§8.5），其中"垂直缺口 ≥ 5 格"是可数值复算的（`205 < 250`），其余两条（贴墙传送门、团队共享箱子）是结构性约束。这条必须在 M5（15 关）之前冻结，否则关卡全部要返工。
